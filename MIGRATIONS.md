# Database Migrations

PostgreSQL / Drizzle ORM migration guide for the VPP platform.

> **WARNING: Never run `drizzle-kit push` against production.**
> `push` rewrites the live schema directly from the schema files with no
> migration history, no journal entries, and no rollback path. It can silently
> drop or alter columns. Production schema changes must go through the
> versioned SQL migrations in `drizzle/migrations/` only.

## Canonical migration set

The linear history lives in **`drizzle/migrations/`**:

| # | File | Contents |
|---|------|----------|
| 0000 | `drizzle/migrations/0000_postgres_baseline.sql` | 161 `CREATE TYPE ... AS ENUM`, 97 `CREATE TABLE`, and the unique/lookup indexes for **every** table defined across the 22 `drizzle/*.ts` schema files. Generated by drizzle-kit from the full schema. |

`drizzle/migrations/meta/_journal.json` + `0000_snapshot.json` are drizzle-kit
generated (journal `version: "7"`, dialect `postgresql`) and must not be
hand-edited — `drizzle-kit generate` maintains them.

The pre-PostgreSQL MySQL migration history (22 legacy `drizzle/*.sql` files, the
duplicate `0000`/`0001` indexes, and the two competing journals in
`drizzle/meta/` and `drizzle/migrations/meta/`) was removed with the PostgreSQL
migration: none of that SQL is executable on PostgreSQL, and no deployed
PostgreSQL database has ever applied it. Databases still running the MySQL
schema must be migrated by data export/import, not by replaying these files.

## Schema discovery

`drizzle.config.ts` globs **all** schema files:

```ts
schema: ["./drizzle/schema.ts", "./drizzle/*-schema.ts"]
```

so `drizzle-kit generate` sees every table, including the ones that were
previously invisible to it (`innovations-schema.ts`, `trust-access-schema.ts`,
`grid-intel-schema.ts`, `nextgen-vpp-schema.ts`).

## How to apply

### Option A — `drizzle-kit migrate` (recommended)

```bash
export DATABASE_URL=postgresql://<user>:<password>@<host>:5432/<database>
npx drizzle-kit migrate
```

drizzle-kit records applied migrations in `drizzle.__drizzle_migrations`; that
table plus `drizzle/migrations/meta/_journal.json` is the source of truth.

### Option B — manual `psql`

```bash
psql "$DATABASE_URL" -f drizzle/migrations/0000_postgres_baseline.sql
```

The baseline is **not** idempotent (`CREATE TYPE` has no `IF NOT EXISTS`), so
apply it only to an empty schema. Use Option A for anything else.

## Adding a migration

1. Edit the relevant `drizzle/*.ts` schema file.
2. `npx drizzle-kit generate --name <change_description>`.
3. Read the generated SQL before committing it. In particular check that
   drizzle emitted the intended `ALTER TYPE ... ADD VALUE` for enum extensions —
   PostgreSQL cannot add an enum value inside a transaction block in older
   servers, and cannot remove one at all.
4. Apply with `drizzle-kit migrate` against a scratch database and run
   `pnpm test` before opening a PR.

## PostgreSQL-specific conventions

* **Identifiers.** Some inherited tables use camelCase column names
  (`userId`, `createdAt`). PostgreSQL folds unquoted identifiers to lowercase,
  so **every camelCase identifier in raw SQL must be double-quoted**:
  `WHERE "userId" = $1`. Drizzle-generated SQL quotes automatically; raw
  `sql\`\`` template literals do not.
* **Placeholders.** Raw SQL uses `$1, $2, …`, not `?`.
* **Generated IDs.** `serial` columns; inserts that need the new id use
  `.returning({ id: table.id })` (there is no `insertId`).
* **Affected rows.** node-postgres returns `{ rows, rowCount }` — use
  `result.rows` for data and `result.rowCount` for affected-row checks.
* **Upserts.** `.onConflictDoUpdate({ target: [...], set: {...} })` /
  `.onConflictDoNothing()` with an explicit conflict target backed by a unique
  index.
* **`updatedAt`.** MySQL's `ON UPDATE CURRENT_TIMESTAMP` does not exist in
  PostgreSQL; columns use drizzle's `$onUpdate(() => new Date())`, which stamps
  the value from the application on every drizzle `update()`. Raw SQL `UPDATE`
  statements must set `"updatedAt"` themselves.
* **JSON.** JSON documents are stored in `text`/`json` columns, so MySQL's
  `JSON_SET` becomes a cast round-trip — `jsonb_set(col::jsonb, '{path}', …)::text`
  — via the `jsonSetText()` helper in `server/sql-json.ts`. Calling `jsonb_set`
  directly on a `json` column fails (`function jsonb_set(json, …) does not exist`).
* **JSON path creation.** `jsonb_set` only creates the *last* segment of a
  path, unlike `JSON_SET`; `jsonSetText()` materialises missing ancestors so a
  dotted path does not silently write nothing.
* **Unique violations.** Code that retries on a duplicate key must test
  SQLSTATE `23505` (`error.code === '23505'`), not MySQL's `ER_DUP_ENTRY`
  / `errno 1062`.
* **Enums.** Enum types are shared, database-level objects named
  `<table>_<column>`. Application string unions must match the enum exactly —
  a value the enum does not contain fails at insert time, not at typecheck
  time.

## Settlement hash chain

The settlement ledger's `event_hash` pre-image is versioned (`v2`) and now covers
every monetary and metering column, not just the descriptive ones. Chains written
by the MySQL-era code (`v1`, amounts uncovered) do not verify under `v2`; since
the PostgreSQL baseline starts empty, existing chains must be re-anchored rather
than carried over.

## Rollback

Drizzle has no down migrations; roll back manually with a new forward
migration. For a fresh deployment the baseline can be undone by dropping the
schema outright (**destroys all data**):

```sql
DROP SCHEMA public CASCADE; CREATE SCHEMA public;
DROP SCHEMA drizzle CASCADE;
```

**Never** roll back by editing an already-applied migration file.
